## これは何のプロジェクトか

**「あつまれ、あれこれ」** は、スマホ1台（または複数台）を囲んで、その場にいる人たちで遊ぶパーティゲーム集です。

出発点は「あれそれどれこれ」という、くまくん（開発者）が学校の課題として作ったアナログのカルタ系ゲームでした。絵カードを並べ、出題者がお題の名前を言わずに特徴を説明し、他の人が当てる、というルールです。そのデジタル版コンパニオンアプリとして開発が始まりました。

その後、お題データを流用した別ジャンルのゲーム（ワードウルフ、時限爆弾など）が増えたため、**「あれそれどれこれ」を1ゲームとして内包する、パーティゲーム集へのリブランディング**を進めています。

### このプロジェクトが大事にしていること

**スマホを「人を分断する道具」ではなく「人を集める道具」として使う。**

AI・音声認識・（将来的な）リアルタイム同期といった新しい技術を使っていますが、目的はすべて **同じ部屋にいる人間同士が向き合うこと** です。技術は主役ではなく、審判役・進行役・記録係に徹します。

象徴的な判断の例：
- **オンライン対戦を意図的に採用しなかった**（「物理カードを囲む」体験が失われるため）
- **AI出題を導入した理由**は「AIがすごいから」ではなく、テストプレイで「出題者ひとりの負担が大きすぎる」と分かったため。人間の負担を取り除き、全員が楽しめるようにするために使った

### 収益化について：広告・ガチャ・課金は入れない

**このアプリには、広告・ガチャ・アプリ内課金を一切入れません。今後も入れません。** 収益化の提案は不要です。

理由：
- **広告**：全員がスマホを囲んで集中している最中に広告が出ると、その場の空気が壊れます。このゲームは「その場の体験」そのものが価値なので、広告と本質的に相性が悪い
- **ガチャ・課金**：「一人で長期間続ける」構造を前提とした仕組みであり、「集まって短時間遊ぶ」このゲームには噛み合わない
- どちらも**プレイヤーを個人に引き剥がす**装置であり、「人を集める」という方針と逆を向いている

維持コストはVPSの月額のみで、AI機能はGeminiの無料枠を使っています。**新規登録に合言葉（`.env`の`REGISTER_CODE`）を必要とする設計**が、結果として利用者数を自然に絞り、無料枠内での運用を成立させています。

## UI・アニメーション・効果音の品質基準（全実装で守ること）

**目指すもの：iOSのアプリのように、分かりやすく・操作しやすく・気持ちよく動くこと。**

ただし**見た目を真似るのではありません。** このアプリの世界観（クリーム色の紙、スタンプ風の赤、丸文字フォント、和のカルタの雰囲気）は維持します。取り入れるのは「なぜiOSが操作しやすいのか」という原則の部分です。

1. **画面遷移にアニメーションをつける**：進む＝右から左、戻る＝左から右。方向を逆にすることで「今どこにいるか」が直感的に分かる
2. **すべての操作に即座の反応を返す**：反応がないと「押せてない？」と連打され、実際に二重処理バグが起きた
3. **押せない状態は見て分かるようにする**：薄く／グレーに
4. **アニメーションは速く（0.2〜0.3秒）**：何度も繰り返すパーティゲームでは、長いアニメーションは確実にストレスになる
5. **効果音は意味を一貫させる**：正解＝上昇音、失敗＝下降音、時間切れ＝ニュートラルなチャイム。タップ音のような常時鳴る音を足すなら、設定でOFFにできること
6. **常時BGMは入れない**：人の声を聞くゲームであり、音声認識も使っているため。将来「場面限定の音楽」（カウントダウン中・結果発表など）は検討するが、常時BGMは不可

**判断に迷ったら**「実際にその場で、複数人がスマホを回しながら遊んでいる状況」を想像すること。派手さより、**迷わないこと・テンポが良いこと**を優先します。

## 技術構成

### フロントエンド
- **UIは単一のHTMLファイル**（`public/index.html`）。画面・CSS・画面まわりのJavaScriptはここに収まっている
- **ただし、テスト可能な独立ロジックは `public/js/` に切り出してよい**（例：`public/js/wolf-logic.js`）
  - 切り出す基準：**DOMに一切触れないルール・計算ロジック**であること。画面の都合を知らない純粋な関数群にする
  - 目的は2つ。①jsdomを立てずに単体テストできる ②将来リアルタイム版などで画面を差し替えても再利用できる
  - 形式はUMD（`window.Xxx` と `require()` の両方から使える形）にする。`<script>` で先に読み込んでからIIFEを動かす
  - **新しいゲームのロジックは、最初からこの形で分離して書くこと。**`index.html` は4800行を超えており、今後もこのパターンで少しずつ分割していく方針
- フレームワーク不使用のバニラJS。IIFE（`(function(){ ... })();`）でラップされている
- スマホ縦画面（幅460px程度）を前提にしたレイアウト
- フォント：Shippori Mincho（見出し）、Zen Maru Gothic（本文）、DotGothic16（数字・スコア表示）
- 画面遷移は「スクリーンベースのステートマシン」：`<div class="screen" id="scr-xxx">` が並び、`goTo(id)` が `.active` の付け替えで切り替える。画面ごとに `enterXxx()` 初期化関数があり、`goTo()` 内でIDに応じて呼び分ける

### バックエンド
- **ConoHa VPS**（メモリ1GB、Ubuntu 24.04）で稼働
- Node.js + Express + better-sqlite3（SQLite）
- pm2で常時起動。別プロジェクトのDiscord Botとプロセスを共存させている
- 公開URL：`https://aresoredorekore.duckdns.org/`（DuckDNSの無料サブドメイン、Let's Encrypt、Nginxでリバースプロキシ）
- Expressが `public/` を静的配信するため、**フロントとバックエンドは同一オリジンの一体型構成**

### リポジトリ構成
```
（リポジトリのルート）
├── .gitignore
├── .env.example
├── server.js
├── db.js
├── package.json
├── public/
│   ├── index.html      ← UI本体（画面・CSS・画面まわりのJS）
│   ├── img/            ← カセットのロゴなど
│   └── js/             ← DOMに触れない独立ロジック（単体テスト対象）
│       └── wolf-logic.js
├── tests/              ← 回帰テスト（npm test で一括実行）
└── docs/
    └── （このファイルなどのドキュメント）
```

`.env`（Gitに含めない）に必要な変数：`PORT` / `NODE_ENV` / `SESSION_SECRET` / `REGISTER_CODE` / `GEMINI_API_KEY`

### 認証・データモデル
- ホスト1人だけがアカウントでログインする方式（bcryptjs + express-session）
- 新規登録には `.env` の `REGISTER_CODE`（合言葉）が必要
- プレイヤー（友達）はログイン不要、名前を入力するだけ
- `topics` テーブル：デフォルトお題＋ホストが追加したカスタムお題
- `matches` テーブル：`player_names` / `rounds`（JSON） / `final_scores`（JSON） / `started_at` / `ended_at`

### AI機能（Gemini API）
- 一部のあそびかたで、お題の説明文をAIに生成させている
- **Google Gemini API**（モデル：`gemini-flash-lite-latest`）を使用。理由：クレジットカード登録なしで無料枠が使えるため
- バックエンドの `POST /api/ai-describe` に `{name, ng_words, hint?, avoid?}` を渡すと `{description}` が返る。`hint:true` なら単語ひとつだけを返す
- **429（レート制限）時は3秒待って1回だけ自動リトライ**する
- フロントからの呼び出しは必ず **`callAI()` ラッパー経由**にすること。ロック・タイマー停止・解除を一箇所で管理している

## デプロイ：GitHub経由の自動デプロイ（重要）

**`git push` した時点で、本番公開が確定します。**

1. `git push`
2. VPS側のcronが**2分おきにGitHubを確認**
3. 更新があれば自動で `git pull` → `npm install` → `pm2 restart`
4. **最大2分後に本番反映**

### 絶対に守る運用ルール

**レビューを受ける前に `git push` しないでください。**

- **commit までは自由に行ってOK**
- **push は、レビュー完了後に明示的な指示を受けてから**

### 補足
- リポジトリ：`https://github.com/kumakunna/aresoredorekore.git`（Public）
- 公開リポジトリのため、**秘密情報は絶対にコミットしないこと**。`.env` は `.gitignore` 済み
- VNCコンソール・SSHポート切り替え・scpによる手動デプロイは**もう不要**（過去の手順書が残っていても従わないこと）
- 万一サーバーが起動しなくなった場合、VPSで `cd /root/backend && git reset --hard HEAD~1 && pm2 restart aresoredorekore-backend` で1つ前に戻せる

## あそびかた（オプション）の設計

**モードは「オプションの掛け合わせ」として再設計されています。** モードカードは廃止されておらず、**「よく使う組み合わせへのショートカット（プリセット）」**として存在します。

### 3つのオプション軸（`state.opts`）

| キー | 値 |
|---|---|
| `describe` | `'human'`（人間が説明）／`'ai'`（AIが読み上げ）／`'hint'`（AIが一言ヒント） |
| `seal` | `'none'`／`'on'`（禁止ワードあり）／`'strict'`（言ったら即アウト） |
| `survival` | `true`／`false`（毎ラウンド最下位が脱落） |
| `showSeal` | 禁止ワードを画面に表示するか（AI出題では既定OFF＝答えがバレるため） |

**旧フラグ（`m.ai` / `m.advanced` / `m.strict` / `m.survival` / `m.oneWord`）を直接参照しないこと。** 必ず導出関数（`isAIDescribe()` / `isSealOn()` / `isSealStrict()` / `optSurvival()` など）を使ってください。独立ゲーム（ワードウルフ等）は従来のMODESフラグにフォールバックします。

### 現在表示されているプリセット（6つ）
通常プレイ／封印ワード／一発アウト／ひとことで、あれ／AI読み上げ／サバイバル勝ち抜き戦

### 非表示中の独立ゲーム（`hidden:true`）
ワードウルフ／時限爆弾／クイズ王決定戦／早押しトーナメント／オークションバトル／秒でこれ

**コードは削除せず残してあります。** リブランディングの際に、「あつまれ、あれこれ」の独立ゲームとして復活させる予定です。

## お題データの仕組み

- サーバーのデフォルトお題＋カスタムお題＋フロント内蔵の `QUIZ_BANK` を、`getPool()` が統合して1つのプールにする
- 難易度は5段階：🟢かんたん／🟡ふつう／🟠むずかしい／🔴ナニソレシラナイ／🟣むりなんだが
- サーバー由来のお題は `TOPIC_DIFFICULTY` テーブルで難易度を付与。テーブルに無い名前は `normal` にフォールバック
- **同一マッチ内で同じお題が重複しない**（`play.usedTopics`）

### 別名（略称）の扱い

**判定は寛容に、表示は正式名称で。**

- `TOPIC_ALIASES` テーブルで、お題に別名を持たせられる。`display` を指定すると表示名を差し替え、元の名前は自動的に別名になる（例：パトカー → 表示は「パトロールカー」、「パトカー」でも正解）
- 略称だけでなく、日常的に同義として使われる言葉も可（例：遊園地 ← テーマパーク）
- **重要なルール**：お題プールに独立して存在する語は、他のお題の別名にしない。これは `getPool()` が毎回自動でチェックして除外するので、テーブルには気軽に書き足してよい
- カスタムお題には別名は付かない

## 記録の仕組み

- 対戦記録は `rounds[]` に `{mode, opts, score_deltas, at}` の形で保存される
- 記録画面では、**オプションのタグ（🤖AI出題／💡一言ヒント／🔒封印ワード／📣即アウト／💀脱落あり）で複数選択（AND）絞り込み**ができる
- 並び替えは「スコア順／更新時間順」
- **過去データ互換**：`opts` が無い古い記録は、`mode` から推測して表示する。それも無ければ「設定の記録なし」と表示。**絶対にエラーで落ちないようにすること**
- 自動保存はON/OFF可能（設定画面）。手動保存ボタンもあり、既存マッチを上書き更新する

## 既知の技術的パターン（新規実装時に踏襲すべきもの）

- `api(path, opts)` — fetchのラッパー。`credentials:'include'`、JSON自動変換、エラー時は `.error` を例外化
- `callAI(body)` — AI呼び出しの共通ラッパー。**必ずこれを経由すること**。`try/finally` でロック解除を保証しており、失敗時に操作不能になるのを防いでいる
- `play` オブジェクト — 進行中ラウンドの一時状態。モードごとに `play.wolfXxx` / `play.bombXxx` のようにプレフィックスで名前空間を分ける
- `state` オブジェクト — アプリ全体の永続的な状態（プレイヤー、選択中モード、オプション、認証情報）
- `scorePlayer(id, delta)` — スコア加算（ハンデ倍率も内部処理）
- `logRound(modeId, scoreDeltas)` — ラウンド結果をサーバーへ送信
- `goTo(id)` — 画面遷移。プレイ画面から離れる際のクリーンアップ（TTS停止・音声認識停止）もここで共通処理している
- 音声コマンドには**クールダウン（2.5秒）**がある。同じ発話が interim/final で複数回拾われるのを防ぐため
- 既存CSSクラスを使い回すこと：`.pk-btn`（フルスクリーン選択肢）、`.hp-chip`（ピル型トグル）、`.reveal-row`（結果一覧の行）など

## 検証について

- **`read_console_messages` は未捕捉例外を拾いません。** 必ず `window.onerror` / `unhandledrejection` を仕掛けて検証すること（過去にこれが原因で、ワードウルフ設定画面のクラッシュを見逃しました）
- 画面遷移を伴う検証では、**非表示要素の `scrollTop` は変更できない**点に注意（過去にタイマー画面の検証で誤った結果が出ました）
- 実際に遊ぶ環境は**スマホ**です。デスクトップ幅だけで確認せず、狭い画面幅でも確認すること
