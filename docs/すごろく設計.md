# カセット「すごろく」設計（第36弾）

## このカセットの方針

**既存のパーティすごろくを真似しない。** 名前・演出・固有の仕組みは一切使わず、
**「マス目を進む」という骨組みだけを借りて、駆け引きは完全にオリジナルで作る。**

入っている5ゲームは、いずれも**「進む」という行為の意味が互いに違う**。

| ゲーム | 「進む」の意味 |
|---|---|
| こまはひとつ | 進む権利を、毎回みんなで奪い合う |
| どこにいる？ | どこまで進んだかを、他人に隠す |
| ふたりでひとつ | どれだけ進むかを、相方と分け合う |
| つうこうりょう | 先に進んでいるほど、進むのが高くつく |
| てふだ | 何マス進むかを、運ではなく自分で決める |

### 手渡しに対応しない理由

- **どこにいる？** … 自分の位置を他人に見せてはいけない
- **てふだ** … 手札を他人に見せてはいけない

### 突然イベントを起こさない理由

- **どこにいる？** … 全員の位置が突然動くと、申告している位置と実際がズレて、
  嘘か本当か以前に本人も混乱する。「毎ターン必ず誰かが申告を求められる」ことでたるみは防げる
- **てふだ** … 有限の手札で駆け引きするので、外部からの突然の変化が、
  積み上げてきた交渉の計算を無に帰してしまう
- **ふたりでひとつ** … じっくり信頼関係を育てる遊びなので、プラス方向のものだけ

### てふだにコインマスを置かない理由

このゲームだけは**止まるマスを自分で選べる**。コインマスを置くと、狙って踏み続けられる。

## 決めごと（指示書に書かれていなかった穴を、この形で埋めた）

### ① あがりを超える出目でも、あがり扱いにする

「ぴったり止まらないと上がれない」にすると、最後の1人が延々と足踏みして置き去りになる。
（原則10：一つの点からすべてを喜ばせる）

### ② こまはひとつ：敗者移動でゴールした時の勝者

駒は1つしかないのに「1位以外も順位に応じて少し動かせる」ので、
**複数の人が同じ駒を動かす**。「ゴールに到達した時、その時に動かした人の勝ち」との整合が要る。

**決めごと**：勝者 → 2位 → 3位… の順に動かす。
**1位が動かした時点であがったら、そこで終了**（敗者移動は行われない＝勝者が横取りされない）。
1位が届かなかった時だけ2位以下が動き、届かせた人が勝つ。
→ 「あと1マス」を残した1位の隙を2位が突く、という山場が生まれる。

**最終順位**：1位はあがらせた人。**2位以下は残りコインの多い順**。
（これがこのゲームでコインを使う理由。勝てない人にも最後まで目標が残る）

### ③ どこにいる？：嘘はシステムが自動で見破る

指摘制にすると「外した指摘のペナルティ」設計が必要になり、話が膨らむ。
申告と一緒に答えた**手がかりが、実際の区画のものと食い違ったら、その場で全員に大きく出す**。

**ただし手がかりは区画をまたがらせる**（「霧が濃い」は3区画で共通、など）。
1区画1手がかりにすると嘘が100%即バレて、誰も嘘をつかなくなりゲームが消える。
重なりがあると「隣の区画までなら通る安全な嘘」が最初から存在し、
遊び込むほど「どの手がかりがどこまで通用するか」が分かってくる。

### ④ どこにいる？：矛盾がバレたら3マス戻る

盤面30の10%。0未満にはしない（落とし穴8）。

### ⑤ ふたりでひとつ：奇数のときの組み分け

- **「3人1組をうまいこと作る」** … 3人組をなるべく均等に散らす（9人なら 3・3・3）
- **「3人1組を1つだけ作る」** … 3人組は必ず1つ、残りは全部2人組（9人なら 3・2・2・2）
- 5人・7人ではどちらも同じ結果になるので、その時は選択肢を出さない

### ⑥ つうこうりょう：同じマスにいる人は同順位

「先に着いた方が上」にすると、盤面を見ただけでは誰が何位か分からない。
このゲームは**順位がそのまま支払額**なので、見て分からないのは致命的。
1位が2人いたら、2人とも全額払う。

### ⑦ てふだ：交渉はターンの頭に1回、買い取りのみ

- **交渉フェーズをターンの頭に置く（時間制）**。常時交渉にすると手番の人が待たされ、
  誰が何をしているか分からなくなる（原則7：1画面につきやることは1つ）
- **買い取りのみ**（コイン → カード）。カード↔カードの交換は提示の組み合わせが
  爆発して画面が破綻するので、入れるなら後から

### ⑧ 効果マスの効果は連鎖しない

効果で動いた先がまた効果マスでも、そこでは何も起きない。
連鎖を許すと1回の手番で盤の端から端まで動くことがあり、「1マスずつ進む」演出も意味を失う。

### ⑨ スワイプの勢いは、出目に一切影響させない

サイコロは「長押ししてスワイプ」で振るが、**勢いで目が変わってはいけない**。
変わると「操作が上手い人が有利」になり、サイコロの意味が消える。
勢いは演出（転がる速さ・音）にだけ使う。

## ファイル構成

```
public/js/sugoroku-logic.js   共通のルール層（盤・サイコロ・移動・コイン・順位・イベント）
                              ↑ 手渡し（index.html）とサーバー（sugoroku-room.js）が同じものを使う
sugoroku-room.js              1人1台の進行役。5ゲーム共通の1本（room.sugoroku）
public/index.html             画面・専用テーマ・手渡しの進行
tests/sugoroku-logic.js       ルール層の単体テスト
tests/realtime-sugoroku.js    部屋の通しテスト
```

**5ゲーム × 遊び方で実装の文脈が8つに分かれる。** これまでで一番
「片方だけ直して、もう片方に反映し忘れる」（落とし穴1）が起きやすい形なので、
共通の計算はぜんぶ `sugoroku-logic.js` の1本に集める。
サーバーの進行役も1ファイル（クイズ王が4ゲームを `quiz-room.js` 1本で持つのと同じ形）。

### 一覧を2か所に作らない（型1対策）

| 一覧 | 置き場所 |
|---|---|
| 5ゲームの性格（人数・マス数・コイン・イベント・手渡し可否・目安時間） | `GAMES` |
| マスの種類 → 見た目と効果 | `CELL_KINDS`（盤面・大画面・決着画面が全部これを引く） |
| 突然イベント | `EVENTS`（各イベントが `games:[...]` を持ち、起こさないゲームには**構造的に配れない**） |

`eventsFor()` は `GAMES[id].events === 'none'` なら、`EVENTS` に何が入っていても必ず空を返す。
条件分岐で防ぐと、イベントを足した人が書き忘れて漏れる（落とし穴4）。

## 演出・UI

`public/js/fx.js` の共通部品を使い、**ゲームごとに書かない**（原則）。

- 駒が進むときは `stagger` で**1マスずつ**。ワープさせない

- 待っている時間は `alive`（見た目はすごろくテーマのCSS側が決める）
- すべての待ちは `hold()` を通す＝**タップで飛ばせる**

人狼・爆弾解除・クイズ王・オークションと同じ方式（CSSスコープを追加専用にし、既存ルールを壊さない）。

- 30〜40マスを**スクロールせずに1画面**に収める（蛇行配置）

片手がふさがっている・手が不自由・画面が滑らない、はどれも実際に起きる。
（「すべての演出はスキップできる」の入力版）

## こまはひとつ（sugograb）の決めごと（着手前に整理・レビュー承認済み 2026-08-18）

つうこうりょうと構造が大きく違うのは「駒が1つしかない」こと。
手番が並び順で回らず、**毎ターン、ミニゲームの結果で決まる**。

### ⑩ 勝利条件（誰があがらせたか）

ミニゲームの勝者 → 2位 → 3位… の順に動かす。
**1位が動かした時点であがったら、そこで終了**（敗者移動は行われない＝勝者が横取りされない）。
1位が届かなかった時だけ2位以下が動き、**届かせた人が勝ち**。

最終順位は、1位＝あがらせた人、**2位以下は残りコインの多い順**。
これがこのゲームでコインを使う理由で、勝てない人にも最後まで目標が残る。

### ⑪ 段階（つうこうりょうと違う）

つうこうりょうは `READY → TURN → RESULT` だが、こまはひとつは

```
READY → MINI（何のミニゲームか画面いっぱいに出す）→ PLAY（ミニゲーム本体）
      → GRAB（勝者が振る・敗者移動）→ RESULT
```

共通の芯にある `pointTurnToPlayable`（並び順で次を探す）は**使わない**。
代わりに `GAME_RULES.sugograb` 側で、ミニゲームの順位から手番列を作る。

### ⑫ 敗者移動の量

**2位＝2マス、3位＝1マス、4位以下＝0マス**（設定でOFFにできる。ONが初期値）。
基準は「勝者の出目（1〜6）より必ず小さく保ち、勝ち筋を薄めないこと」。

### ⑬ 手渡しでの同時入力系（案3を採用）

じゃんけん・指の数当ては「全員がせーので出す」遊びだが、1台では同時に入力できない。
**手渡しでは、1人ずつ画面に伏せて入力して回す。**

採らなかった案と理由：
- 画面の外で出して結果だけ入力する … アプリが公平に判定できなくなる
- 手渡しでは同時入力系を出さない … **「4系統から毎回ランダムに選んで勝者を分散させる」という
  このゲームの核を、遊び方によって半分にしてしまう**

**宿題**：1人ずつ回すぶん1ターンが伸びる。実装後に**実測して、目安時間（15分）が
手渡し版の実態と合っているかを確認する**。ずれていれば手渡し版だけ表示を調整する。

### ミニゲームの決めごと

- **4系統から1つずつ、計4種**で始める。2系統だと「その2つが得意な人が連勝」する状態で
  検証することになり、このゲームの核（勝者の分散）を確かめられない
- **クイズ最速は `public/js/quiz-bank.js` の既存問題を流用**（新しい問題プールを作らない）
- **同時入力系は、入力が揃わない場合の扱いを最初から `settleAfterMemberGone` と
  タイムアウト代行の型に乗せる**。あとから経路ごとに足さない（落とし穴17）

## ふたりでひとつ（sugopair）の決めごと（着手前に整理 2026-08-19）

つうこうりょう・こまはひとつと構造が違うのは、**駒が「人」ではなく「組」に付く**こと。
そして**新しい止まり方**を持っている。

### ⑭ このゲーム固有の「止まり方」（最初に固める）

これまでの2つは「手番の人が消える」＝**待つ相手が1人**だった。
ふたりでひとつは**2人の合計が出目に一致するまで確定しない**ので、
**相方が消えると、配分が永久に一致しない**。共有の駒より深刻な止まり方になる。

決めごと：
- **相方がいなくなったら（切断・退室・kick）、残った1人が出目を全部使える。**
  「相談する相手がいないのに相談を待つ」状態を作らない。
  組の人数が変わったことは、残った人にその場で知らせる（黙って仕様を変えない）
- **交渉が時間内にまとまらなければ、自動で等分する。ただし端数は切り捨て**（指示書どおり）。
  例：出目5なら 2＋2 で1マス分が失われる。「ちゃんと交渉した方が得」という誘導
- 待つのは**組ごと**。ある組がまとまっていなくても、まとまった組は先へ進める
  （組をまたいで待たせると、1組の停滞が全員を止める）

### ⑮ 段階

```
READY → ROLL（組の代表が振る）→ SPLIT（2人で配分を入力・合計が出目と一致で確定）
      → MOVE（組の駒が進む）→ RESULT
```

手渡し（1台）では、**組ごとに順番に回す**。相談は口頭でできるので、
こまはひとつのような「伏せて入力」は要らない——**むしろ相談は声に出してよい**のが
このゲームの芯なので、2人が同じ画面を見ながら入力する形にする。

### ⑯ 順位

コインを使わないので、**ゴール到達順 → 進んだ距離 → 同着**（性格表の tiebreak='same'）。
組の順位なので、決着画面は**人ではなく組で並べる**。

### ⑰ ペアの決め方

**ランダム。自分たちで選ばせない**（組み合わせの妙も含めた遊び・指示書どおり）。
奇数のときは決めごと⑤の選択画面を出す。

## どこにいる？（sugohide）の決めごと（着手前に整理 2026-08-19）

**秘密設計の本丸。** 自分の位置は自分にしか見えず、申告では嘘をついてよい。
人狼の「正体を隠す」を「位置を隠す」に置き換えた遊び。

### ⑱ 秘密の線引き（ここを最初に固める）

| もの | 誰に見せるか |
|---|---|
| **実際の位置** | **本人だけ**（`privateFor`）。公開ビューにも**大画面にも**入れない |
| 申告した位置 | 全員（それが遊びの材料） |
| 申告した手がかり | 全員 |
| 誰が申告を求められているか | 全員 |
| 矛盾が出たかどうか | 全員（ここが一番盛り上がる場面） |
| あがったかどうか | 全員（ゴール判定はサーバーが実位置で自動的に行う） |

**嘘の申告で勝利を宣言することはできない。** 申告は「他のプレイヤーに向けた発言」にすぎず、
ゴール判定は自己申告と無関係にサーバーが実位置で行う（指示書どおり）。

`tests/secrecy-gates.js` と同じ形の恒久テストを最初から書く。
見るのは2層：**公開ビューに実位置が入っていないこと**と、
**画面のDOMに他人の実位置が出ていないこと**。

### ⑲ 手がかりは、区画をまたいで重ねる

盤を区画に分け、区画ごとに「そこにいる人にしか分からない手がかり」を持たせる。
ただし**1区画1手がかりにしない。** そうすると嘘が100%即バレて、誰も嘘をつかなくなり、
このゲームの核が消える。

**同じ手がかりを複数の区画に持たせる**（「霧が濃い」は3区画で共通、など）。
すると「隣の区画までなら通る安全な嘘」が最初から存在し、
遊び込むほど「どの手がかりがどこまで通用するか」が分かってくる。

手がかりは20種類ほど用意する（指示書どおり）。

### ⑳ 矛盾の判定は自動。バレたら3マス戻る

申告と一緒に答えた手がかりが、実際の区画のものと食い違ったら、その場で全員に大きく出す
（`FxKit.banner`）。指摘制にすると「外した指摘のペナルティ」設計が必要になり話が膨らむ。

戻る量は3マス（盤面30の10%）。0未満にはしない。

### ㉑ 申告を求める相手は、まだ申告していない人から選ぶ

完全ランダムだと同じ人に3連続で当たり得る。**毎ターン必ず誰か1人が申告する**のが
たるみ防止の仕掛けなので、偏ると仕掛けが効かない。
一巡したら、また全員から選び直す。

### ㉒ 突然イベントは起こさない（性格表で `events:'none'`）

全員の位置が突然動くと、申告している位置と実際がズレて、
嘘か本当か以前に本人も混乱する。`eventsFor()` が構造的に空を返すので、
イベントを足した人が書き忘れても漏れない。

### ㉓ 手渡しには対応しない（性格表で `handoff:false`）

自分の位置を他人に見せてはいけないので、1台を回す形では成立しない。

## 部屋版（1人1台）の決めごと（2026-08-21）

第36弾-17までの時点で、部屋版は**器（HTML）だけがあって描画も操作も無い**状態だった。
それを「部屋版も完成」と報告していた。原因と対策を残す。

### ㉔ 描き分けは `rtRenderCurrent` ひとつに集約する

抜けた原因は、部屋の描き分けが2か所にあったこと。

| 振り分け | 判定のもと | すごろくの扱い |
|---|---|---|
| `rtRenderCurrent()` | 画面id | 足した |
| `rtRender()` | **ゲームid** | 無い → 人狼の描画に落ちる |

`goTo` が呼ぶのは `rtRender()` なので、**画面に入った直後だけ盤が空**になっていた。
「どこにいる？」だけテストが緑だったのは、あとから届く `wolf:you` が
`rtRenderCurrent()` を通していたため。

`rtRender` は `rtRenderCurrent` を通すだけにし、`RT_GAME_SCREEN_IDS` は
`RT_GAME_SCREENS` から導く形にした。手書きの一覧が2つ消えたので、
ゲームを足した時に片方だけ更新されることが構造的に起きない（落とし穴4）。

### ㉕ 操作の入口は、手渡し版と同じ部品を通す

- `bindDiceGesture(要素, opts)` … 長押ししてスワイプの判定。
  出目に勢いが混ざらない形（判定は `SugorokuLogic.rollGesture` だけが持つ）はそのまま。
- `sugoBuildInput(入れ物, ミニゲーム, 出題, 締め切り, 出したとき)` … ミニゲーム4系統の入力。
  **正解かどうかの判定を持たない**ので、部屋版では答えを配らずに済む
  （端末を覗いても答えが無い）。連打のタイマーを止める手を返す。

### ㉖ 言い回しはルール層に置く（画面に直書きしない）

手渡し版の画面に書いてあった言葉を部屋版へ写すと、必ず片方だけ古びる（落とし穴2）。
`SugorokuLogic.tollWords` / `grabWinWords` / `drawWords` / `grabEndWords` /
`goalEndWords` / `pairTurnWords` / `pairGoalWords` / `pairFirstWords` / `splitWords` と
`SugorokuHide.sayWords` に集め、両方の画面がそこを通る。

`tests/room-paths.js` が「その言い回しが `index.html` に直書きされていないこと」を
機械照合するので、画面の側に書き戻すと赤くなる。

### ㉗ 申告で嘘をつけるのは「区画」だけ

区画は5つとも選べるが、**手がかりは自分に見えているものしか出さない**。
全部の手がかりを選べると、矛盾が起きようがなくなり遊びが成立しない。
嘘の区画にその手がかりが無ければ、その場で矛盾になる——それがこの遊びの綱渡り。

自分の本当の居場所は、自分の画面にだけ小さく出す（公開ビューには入っていない）。

### ㉘ 分け合いは、出た目より多い数を端から出さない

部屋版は各自が自分の数だけを入れる（相方の数も見える＝声に出して相談する遊びだから）。
合計が出た目とぴったり合った時だけ、サーバーが確定する。
足りない・多すぎるの一言も `splitWords` が持つので、手渡し版とまったく同じ言葉になる。

### ㉙ 大画面には、盤そのものを出す

大画面は**部屋の全員が囲む卓**なので、盤が出ていないと意味がない。
ここに分岐が無かったため、すごろくの大画面は人狼の大画面に落ちて
**全員が💀（死亡）で並んでいた**。段階の名前も生のid（`split`）のままだった。

盤の組み立ては `sugoFillBoard` 1つに集約し、**手渡し・部屋・大画面の3つが同じものを通る**。

### ㉚ 段階の名前は、ゲームごとに持つ

`RT_PHASE_LABEL` は全ゲーム共通の対応表で、`play` には**爆弾解除の「解除中」**が入っている。
こまはひとつも段階名 `play` を使うので、共用すると
「ミニゲームで出しています」の場面に「解除中」と出る（落とし穴2）。
すごろくは `SUGO_BIG_PHASE` を自分で持ち、共通の対応表を上書きする。

### ㉛ 大画面が「どこにいる？」で何も置けないのは、隠しているからではない

大画面には `privateFor` が届かない。実位置は公開ビューに入っていないので、
**持っていないから置けない**——これが正しい形。
`rtSugoByCell(v, null)` を通すので、隠す処理を書き忘れるという事故が起きない。

大画面に出るのは「申告した区画」だけ。盤は出るが、駒は1つも乗らない。

### ㉜ 称号：完成しているカセットの中で、すごろくだけ空だった

`titles.js` にカセット項目が無く、手渡し・部屋のどちらでも数えていなかった。
他の5カセットには全部あるので、**すごろくで遊んだ人にだけ何も残らない**状態だった。

数えるもの（`STAT_SHAPE.sugoroku`）:

| カウンタ | 意味 |
|---|---|
| `plays` / `wins` / `goals` | 遊んだ・1位になった・あがりに着いた |
| `tollPlays` … `hidePlays` | どのゲームを遊んだか（4つ） |
| `tollWins` … `hideWins` | どのゲームで1位になったか（4つ） |

**あがれば、1位でなくても1つ手に入る**（`icon-sugo-goal`）。
勝ち負けと関係なく褒める——大切なこと5と原則7の形。

二つ名の後ろは、4つのゲームの見せ場を1つずつ:
関所やぶり（つうこうりょう）／ひとりじめ（こまはひとつ）／
あうんの呼吸（ふたりでひとつ）／かくれみの（どこにいる？）。

### ㉝ 決着の知らせに id を入れる

「自分が1位か」を名前で当てていると、同じ名前の人が2人いた時に取り違える。
`resultView` の各行に id を入れた。**ふたりでひとつだけは「組」のid**なので、
自分の枠（`v.players[].groupId`）から読み替える。

### ㉞ 数えるのは手渡し版と部屋版の両方。対応表は1つ

部屋版は `rtTitleGainFor`、手渡し版は `awardSugorokuTitles`。
ゲームid→カウンタ名の対応表（`SUGO_TITLE_KEY`）は**1つを両方が引く**。

手渡しは1台を回すので「自分」は名簿の中の1席。
誰が持ち主か分からない時（ログインしていない等）は、遊んだ回数だけを数える。
席のidは `sugoStart` が並び順から作る（`h0`, `h1`, …）ので、
**名簿のidをそのまま使ってはいけない**（並び順で読み替える）。

### ㉟ 「完成カセットに称号があるか」を機械照合する

この抜けに誰も気づかなかったのは、照合が無かったから（落とし穴4）。
`tests/inventory.js` の `READY_CASSETTE_IDS`（index.html の CASSETTES から自動抽出）を
正本にして、`tests/titles.js` が
「数える箱があるか」「パーツが1つ以上あるか」を全カセットぶん回す。
新しいカセットを完成させた瞬間に、称号を足すまで赤くなる。

## てふだ（sugohand）の決めごと（着手前に整理 2026-08-21）

「進む」の意味は**何マス進むかを、運ではなく自分で決める**。
サイコロを振らないので、他の4つと違い、**運の要素をどこに置くか**を先に決める必要がある。

### ㊱ ぴったり上がり（このゲームだけ、決めごと①の例外）

> **この1点だけは、人の判断を待っている。**
> 勝敗条件そのものなので、着手前に確認をお願いしている。
> 実装では sugohand のあがり判定1か所に閉じてあり、
> 「超えたらゴール」に戻す場合もそこだけを直せばよい形にする。

カセット共通の決めごと①は「ゴールを超えたらゴール」。
サイコロは自分で選べないので、超えた分を切り捨てるのが親切だった。

**てふだは自分で選べるので、切り捨てると「大きい札から出すだけ」になる。**
ゴールぴったりの数でなければ出せない、とすることで:

- 大きい札を先に使うと、最後に必要な小さい札が無くなる
- 「あと3マス」の時に3が無ければ、**誰かから買うしかない**（交渉が効く）

つまり、㉙が無いと決めごと⑦（交渉）が飾りになる。例外にする理由はここ。

### ㊲ 手札は10枚・数字は1〜6・合計は33〜38に揃える

盤は30マス。合計35前後なら「5マスぶんは無駄にできる」計算になり、
出し方を間違えると届かなくなる——ぴったり上がりの緊張が効く幅。

**配った時点で合計に差があると、それだけで勝負がつく。**
各自の合計が33〜38に収まるまで配り直す（人数×10枚を1〜6から作る）。
これは公平性の話なので、ルール層で保証してテストで固定する。

### ㊳ 補充はしない。出せる札が無い時は進めない（そのかわりコインが入る）

有限の手札で駆け引きするゲームなので、補充すると緊張が消える。
出せる札が無い＝進めない時は、責める場面にしない。
**入った方を主語にする**（つうこうりょうの「かわりに コイン+◯」と同じ思想・原則7）。

### ㊴ 全員が進めなくなったら、その時点の位置で決着

補充が無いので、誰もゴールできないまま終わる可能性がある。
打ち切り条件を置かないと**永久に終わらない**（落とし穴17の親戚）。
一巡して誰も進めなかったら決着とし、盤の位置 → コインの順で並べる。

### ㊵ 交渉は「売り札を出す」→「手番の人が1つ買う」の2段

決めごと⑦（ターンの頭に1回・買い取りのみ）を、画面の形に落とすとこうなる。

1. **提示**（時間制・手番の人以外）… 手札から1枚と値段を選んで出す（任意・1人1枚まで）
2. **買う**（時間制・手番の人だけ）… 出ている売り札から1つ買う、または買わない

手番の人だけが買えるのは、常時交渉にすると誰が何をしているか分からなくなるため
（原則7：1画面につきやることは1つ）。
提示は全員が同時にできるので、待たされる人が出ない。

### ㊶ 見せるもの・隠すもの

| もの | 誰に見える | 理由 |
|---|---|---|
| 自分の手札の数字 | **本人だけ**（privateFor） | 見えたら駆け引きが消える |
| 手札の**枚数** | 全員 | 残り枚数は読み合いの材料。数字は分からない |
| 手札の合計 | 誰にも出さない | 実質的に「あと何マス進めるか」が割れる |
| **提示中の売り札**（数字と値段） | 全員 | 交渉に必要。出すこと自体が「その札を持っている」という情報のコスト |
| 買った・買わなかった | 全員 | 誰が何を手に入れたかは、その後の読み合いの材料 |
| コインの残り | 全員 | つうこうりょうと同じ |

### ㊷ 人がいなくなった時

- 提示していた売り札は取り下げる（買えない札を出したままにしない）
- その人の手番は飛ばす
- 待ち人の数え直しは `settleAfterMemberGone` を通す（落とし穴17）
- **買った直後に売り手が消えても、取引は成立したまま**（コインと札はもう動いている）

### ㊸ 突然イベントは起こさない（性格表で `events:'none'`）

有限の手札で積み上げた計算が、外からの変化で無に帰す。
`eventsFor()` が構造的に空を返すので、イベントを足した人が書き忘れても漏れない。

### ㊹ 手渡しには対応しない（性格表で `handoff:false`）

手札を他人に見せてはいけないので、1台を回す形では成立しない。

## 棚に出してはじめて分かったこと（2026-08-21・てふだの実サーバー検証）

### ㊺ 「棚に出す」には、同じ形の手書き一覧が4つある

`ready:true` にしても遊べない。順に引っかかった:

| 一覧 | 無いとどうなるか | 気づいた場所 |
|---|---|---|
| `tests/inventory.js` の `RT_START_MIN_CONFIG` | テストが始められない | 検出網 |
| `GAMES[id].ready` | `not_ready` で始まらない | 検出網 |
| カセットの `games:[...]` | **ゲーム選択に出てこない** | 実サーバー |
| `RT_GAME_SCREENS` / 画面の `GAMES` | 「まだ1人1台に対応していません」 | 実サーバー |

**照合の向きが片方しか無かった**のが原因。カセット→進行役は見ていたが、
進行役→カセット・進行役→画面が無かった。3つの逆向きを `tests/room-paths.js` に足した。

### ㊻ 「設定は出るのに、何も起きない」を作らない

てふだの設定画面を見ていて気づいた。5ゲーム中4ゲームで、
決めても何も変わらない設定が出ていた:

- どこにいる？・てふだ … `events:'none'` なのに「突然のできごと」が出ていた
- こまはひとつ・ふたりでひとつ … `events` を持つ性格なのに、`EVENTS` に1つも無かった

前者は `eventsFor()` から出し分けを導いて解決。後者は**できごとを足した**
（かぜが つよい／おふだ ひろい／おいかぜ）。効き目は共通層に置き
（`loserStepsWith` / `moveBonusCoins` / `pairBonusSteps`）、手渡し版と部屋版の両方が通る。

`tests/sugoroku-logic.js` に2つの照合を足した:
「できごとを持つ性格のゲームには、実際に起きるできごとがある」
「どのできごとにも、効き目のある居場所がある」。

### ㊼ 待ち相手が全員いなくなった段階が続く時、段階ごとに締め切りを待たない

てふだで、手番の人が切れたまま「売り札を出す → 買う → 札を出す」と続くと、
各段階で25秒ずつ待たされた。止まりはしないが、残った人はただ待つ（落とし穴17の親戚）。

**芯（`realtime.js`）で直そうとして、人狼を壊した。**
「朝」のように*誰も待っていないが見せるための段階*まで飛ばしてしまい、
`tests/abnormal.js` が 7/11 に落ちた。段階の意味はゲームごとに違う。

すごろくの `advance` の中だけで解いた——「人を待つ段階なのに、待つ相手が
1人もいない時だけ先へ進める」を回数上限つきで。共通化してよい層と、
そうでない層がある。
