## 1. 手渡しと部屋の並走を安全にする（第41弾から切り出し・2026-09-07）

### 何を外したか

指示41 2-4 の当初案：

> 【1台専用・部屋あり】
> このカセットは、1台のスマホをまわして遊びます。
> **部屋はそのまま残ります。ほかの人のスマホは待ちます。**
> 　　　[ はじめる ]　　やめる
>
> 部屋を持ったまま1台専用を選んだら：部屋は残り、他の人の画面は
> 「いま、1台のスマホで遊んでいます」で待つ。終わって戻ると待合に復帰

### なぜ外したか

**第33弾B-3が塞いだ穴を、開け直すものだった。**

`public/index.html` の該当箇所にこう書いてある：

> 部屋を持ったまま「1台のスマホで遊ぶ」へ入らない。
> 部屋に紐づいたまま手渡しへ進むと、「もう一度」や「ゲームを終了」が
> **部屋の方に流れて、状態が混ざる（実機で起きた）**。

本人の裁定（2026-09-07）：

1. 第33弾の安全策は**実際に実機で起きた事故の記録**。
   指示41 2-4 を書いた時にこの事故を確認しておらず、
   「部屋を残す」は机上で考えた理想の流れだった
2. 状態の混ざりを直したうえで部屋を残すのは、確認画面1枚の話ではなく
   **独立した実装作業**。指示41に混ぜると「1指示1つの使える状態」から外れる
3. **安全性が実装の完成度より優先される。**
   分離できる保証が無い状態で、部屋を残す方を選ぶ理由がない

### 第41弾ではどうしたか

確認画面の文面を、閉じてから進む形に確定した：

```
このカセットは、1台のスマホをまわして遊びます。
部屋を閉じて、1台のスマホで遊びますか？
      [ 部屋を閉じて はじめる ]    やめる
```

実体は `public/js/ui-text.js` の `WAY.leaveRoom`。
進行役なら「閉じて」、参加者なら「抜けて」。

### 再開する時に確かめること

**「部屋を残す」を実装する前に、まず混ざりを直す。** 順番を逆にしない。

1. 手渡し中の「もう一度」「ゲームを終了」が、**部屋ではなく手渡し側に流れる**こと
   （第33弾B-3で実機で壊れたのはここ）
2. 待っている人の画面に「いま、1台のスマホで遊んでいます」が出ること（新規）
3. 終わって戻った時に待合へ復帰すること
4. 上の3つが揃ってから、`WAY.leaveRoom` を「残す」形に書き換える

**この宿題の完了条件は、確認画面の文面ではなく、上の1〜3が動くこと。**

### 未確認のまま残っていること

第33弾B-3のコメントにある「実機で起きた」は、
**コード内のコメントとしてのみ**受け取っている。
当時の実機確認の記録そのものは、本人もこちらも見ていない。
再開時、もし混ざりが再現しないなら、この前提から確かめ直す。

## 2. 検査に複製された「カセットを押す」4行（第41弾で気づいた・2026-09-07）

### 何が起きているか

```js
cart.click();
if (activeScreen(doc) === 'scr-shelf') cart.click();  // 中央でなければ2回目で選択
await sleep(win, 100);
```

この並びが **tests/ の8ファイルに53箇所** 複製されている。

| ファイル | 箇所 |
|---|---|
| `smoke.js` | 37 |
| `rt-screens.js` | 7 |
| `wolf-vote.js` | 4 |
| `harness.js` | 1 |
| `shelf.js` | 1 |
| `secrecy-gates.js` | 1 |
| `fixes36.js` | 1 |
| `playthrough.js` | 1 |
| **合計** | **53** |

数え方：`.cart[…]` から取った要素を押し、その直後に「まだ棚なら押し直す」を
置いている箇所を1つと数える。押し直しの2つの書き方
（素のものと `&& !doc.querySelector('.cassette-warp')` 付き）を両方数える。

> **訂正（2026-09-08）。** 最初この節には「6ファイルに47箇所」と書いていた。
> 両方とも誤り。
>
> - 書いた内訳（34+5+4+1+1+1）の**合計は46**で、見出しの47と合っていなかった
> - その内訳は、変数名が `cart` で、行が `cart.click();` で終わるものだけを
>   数える grep から出ていた。**`.cassette-warp` 付きの書き方と、
>   受け手が `cart2`／`bomb`／`wolf` の箇所が丸ごと落ちていた**
>
> 数え直しは2通りの方法で別々に行い、どちらも同じ 53／8 に着いた。
> **書いた数字を、確かめずに宿題として残していた**——
> 宿題の側にも「確かめていないこと」があった、という記録として残す。

### なぜ宿題になるか

第41弾でカセットの後ろに「遊び方の確認」が挟まった時、
**後続が `waitScreen` の site は自動で通り抜け、`sleep` の後に分岐する site だけが落ちた。**
落ちた順に1つずつ直したので、いまは緑だが——
棚の流れに次に1段挟まった時、また同じことが起きる。
しかも「どこが落ちるか」は後続の書き方次第なので、事前に読み切れない。

手で複製した並びに、あとから前提が変わる形（落とし穴1・4）。

### やること

`tests/harness.js` に `openCassette(win, doc, id)` を1つ置き、
各ファイルのローカルな `toModeScreen` 等がそれを呼ぶ形に寄せる。
**53箇所すべてではなく、まずローカルの補助関数を寄せれば大半が片づく。**

寄せる先の候補（呼ばれている回数）：
`pickCart`（shelf 15回）・`toModeScreen`（playthrough/secrecy-gates/smoke 22回）・
`setupPlayers`（4ファイル 20回）・`openCassette`（play-way 5回）・
`gotoModeScreen`（smoke 4回）。
**この5本を寄せれば、53箇所の大半がその下に入る。**

### 完了条件

棚とカセットの間に画面を1つ足す変更を入れた時、
**直す場所が1箇所で済むこと。**

## 3. お気に入り（第41弾 2-6 を削った・2026-09-08）

### 何を外したか

指示41 2-6「お気に入り（最小）」——
タイルの隅に☆、押すと★になって0.4秒かけて先頭側へ滑る、というもの。

2-6 自身に**「指示が大きくなりすぎたら、ここは削る候補の筆頭。
削る場合は報告する」**と書かれている。その条項を使った。

### なぜ外したか

**1つは、指示41が実際に大きくなったこと。**
入口の作り直し・棚の1列化と輪・中央の帯・人数チップ・遊び方の確認・
役割の切り替えまでで、1つの指示に入る量を超えている。

**2つめは、2-2 と静かにぶつかること。**
2-2 は「固定順（棚の設計順）。**遊ぶたびに並びを変えない**（体の記憶を壊さない）」
と決めている。お気に入りは、まさに並びを変える機能——
2-6 は「お気に入りだけ先頭側へ」と書いているので矛盾ではないが、
**★を1つ付け外しするたびに棚の並びが変わる**のは事実で、
体の記憶という観点では同じ性質の揺れになる。

いまカセットは6枚で、**輪にしたので端が無く、どこからでも3回以内に届く**。
並べ替えて短縮できる距離が、そもそも小さい。

### 再開する時に確かめること

1. カセットが**10枚を超えているか**（6枚では効き目が薄い）
2. ★の付け外しで並びが変わることを、遊ぶ人がどう感じるか——
   2-2 の「体の記憶」と実際にぶつからないか、実機で確かめてから入れる
3. 入れるなら、置き場所は端末（未ログイン）とサーバー（ログイン）の両方。
   2-10 の秘密情報の表に「お気に入りは本人だけ」と既に書いてある

### 完了条件

**★を付けても、次に開いた時に「いつもの場所」が壊れていないこと。**
機能が動くことではなく、体の記憶が保たれることの方が条件。
