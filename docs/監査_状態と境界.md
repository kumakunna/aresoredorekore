# 監査：状態と境界（第35弾B・型2の先回りリスト）

「境界をまたいで生き残る可能性のある状態変数」と「どの境界でリセットされるべきか」の一覧。
型2のバグ（リセット判断の誤り）を**実機で偶然踏むのではなく、一覧で先回りして確認する**ための正本。
網羅は目指さない——検証や実装で新しい状態に出会ったら1行足す運用（時間をかけすぎない）。

書式：`確認` 列は ✅=確認済み（日付） / 仕様=持ち越しが意図 / 未=部屋ゲーム等でこれから確認

## ルールを読んで「準備OK」（第37弾・実装前に先回りで書いた）

部屋でゲームを選んでから始まるまでの間だけ生きる状態。**「誰が押したか」はサーバー、
「誰が読んだか」は端末**に置く。前者は全員に見せる公開情報、後者はその人の端末の都合。

| 状態 | 置き場所 | あるべき境界 | 確認 |
|---|---|---|---|
| `member.readyGame`（この人が準備OKを押したゲームid） | サーバー | **ゲーム変更・再戦（reset）・ゲーム開始**でリセット。退室・kickではその人ごと消える。「いまのゲームのidと一致するか」で見るので、ゲームが変わった瞬間に自動で無効になる。落とす場所は `clearReady()` の1か所だけ（落とし穴17） | ✅9/2（tests/room-ready.js が5つの境界を実サーバーで1つずつ回す） |
| `readyTally()`（公開スナップショットの `ready`） | サーバーが計算 | 都度計算（持たない）。**数えるのは「つながっているプレイヤー」だけ**——切れた人・大画面を待たない（落とし穴17・`settleAfterMemberGone` と同じ考え） | ✅9/2（切断・大画面・途中参加・ホスト交代を実サーバーで確認） |
| `rtRulesSeen[gameId]`（このゲームのルールを読んだ） | 端末（メモリ） | **ゲームごとに保持・再戦でも保持・部屋を出たらリセット。** 「部屋単位で1回」ではなく「その人の端末で1回」なので、途中参加した人には必ず出る | ✅9/2（2周目に読む画面をはさまないことを確認） |
| ホストが「ルールを見る」を押したか | どこにも持たない | **状態にしない。** 相談の前に「見た」を知らせる意味が無いので、記録も配信もしない（指示37 2-2） | ✅9/2（押しても何も送らないことを確認） |
| `rtPeekModeId`（下見しているモード） | 端末（メモリ） | **画面境界**。モード一覧に戻ったら必ず null（見ただけで選んだことになると事故になる） | ✅9/2 |

## すごろく（第36弾・実装前に先回りで書いた）

ターン制なので「手番」「巡」という、他のカセットに無い境界が増える。
実装前にここへ書き出したのは、`w.event` の失効を巡境界ではなく段階境界に置いていて
