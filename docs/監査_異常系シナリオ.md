# 監査：異常系シナリオ（第35弾フェーズD）

通信・異常系・状態復帰の検証台帳。**行の一覧は`tests/inventory.js`の`ABNORMAL_SCENARIOS`が正**で、
全シナリオぶんの行があることを`tests/room-paths.js`が機械照合する。
原則は一貫して**サーバー権威・クライアント表示**（学校のオフラインイベント本番を想定）。

## 検証観点（指示35D第2部・全シナリオに適用）

1. サーバーの状態が壊れない（不正・重複・手遅れの入力はサーバー側で拒否）
2. 他のプレイヤーの画面が正しく更新される
3. 復帰した本人が、サーバーの現在状態に基づいた正しい画面に戻れる
4. 復帰時に秘密が漏れない（再接続レスポンスに他人の秘密が無い）
5. フェーズAの退室・在室判定が異常系でも一貫

## これまでの検証との重なり（二重にやらないための整理）

- `d01`/`d02`の骨格＝`settleAfterMemberGone`（切断・退室・kickの3経路集約）はA/Bで実機・テスト済み。
  Dでは「**ゲームごとの進行が**切断・タイムアウトで壊れないか」を残りのゲームでも見る
- `d04`の骨格＝リロード→部屋rejoin（memberId継承）はB/Cで多数実施済み。Dでは待機中・ゲーム中・結果画面の
  3局面×代表ゲームを系統立てて通し、**古いローカル状態で描画していないか**（落とし穴18の観点）を見る
- `d07`の骨格＝サーバー門（taken/already_bid/nothing_open/self_vote等）はBで実測済み。Dでは「同時」性
  （同フレームの競合）を突く
- `d09`の骨格＝`room:peek`＋`dropRoom`（フェーズA）で在室判定済み。Dでは古いQR・解散済みコードの直叩きを見る
- `d05`のsocket.ioバッファリング仮説・`d14`のチェックリストはB/Cレビューからの申し送り（予約済み）

## 実機（スマホ）でしか再現できない部分

`d05`のスリープ→復帰（OSによるsocket切断・タブ凍結）は検証環境では完全再現できない。
自動検証で「切断→溜まった操作→再接続」の等価シナリオを先に潰し、**実機チェックリスト**を作って
くまくんに依頼する（このフェーズの成果物の1つ）。

## 発見メモ

- **8/16 d07/d08/d09/d11/d13 をサーバー直叩きの恒久テストで確認（tests/abnormal.js・npm test連結・6/6緑）**：
  サーバーは5シナリオとも既に堅牢だった。d07=同フレーム二重投票は上書きで1票のまま・開始二重は
  already_started拒否＋非ホストはnot_host／d11=締切成立と同フレームの遅れ票はwrong_phase拒否・集計1回／
  d09=存在しない/解散済みコードはjoin・peekとも正しく拒否／d08=同memberIdは同じ枠に復帰（名簿増えず）・
  接続中の同名は別人として増える（設計どおり）／d13=決着時のDB書き込み失敗は**6つの記録関数それぞれの
  try/catch＋警告ログで吸収**され、プロセスは落ちずゲームは決着し部屋も操作可能
- **d13の注記**：DB失敗時、記録は失われリトライは無い（w.recorded=trueが先に立つ）。進行を守る設計としては
  正しく、ディスク満杯等はサーバーログ「対戦履歴の保存に失敗しました」で気づける。気づき[低]として記録

  締切成立→集計へ（切断者を無期限に待たない）→数秒後に同じmemberIdで復帰すると同じ枠に戻り、
