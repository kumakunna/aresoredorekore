もとは CLAUDE.md の「3. 今日までに何度も踏んだ落とし穴」。2026-10-23、使用量を減らすためにここへ移した（**中身は一字も変えずに移しただけ**）。
番号は前と同じ——コード・テスト・docs のコメントにある「落とし穴N」は、この番号を指す。
**どの作業の前にどれを読むか**は CLAUDE.md の「3. 読む所の目安」にある。新しい落とし穴は、ここの末尾に番号を続けて足す。

## 今日までに何度も踏んだ落とし穴（再発防止リスト）

1. **並走する実装の片方だけ直して、もう片方に反映し忘れる**（手渡し版と1人1台版、通常版と競争版など）
2. **借りたロジック・用語が、その世界観のまま漏れる**（別ゲームの言葉がそのまま残る）
3. **専用テーマ・スタイルの適用範囲が、実際にプレイ中の画面だけに限定され、設定・ウィザード・大画面が漏れる**
4. **手書きの一覧・条件分岐に、新しい項目を登録し忘れる**。可能な限り一覧化・自動判定（データから導く）にする
5. **IDやモード名を変えると、記録・履歴に古いIDが直書きされている箇所が取り残される**。`grep`で参照箇所を全部洗い出し、テストで固定する
6. **匿名性・秘密情報が、新しい画面や機能で漏れる**
7. **タイマー・カウントダウンが、新しいフェーズをまたぐと重複したり止まったりする**。既存の共通処理を使う
8. **上限・下限のチェックが片方向にしか効いていない**
9. **1つの修正が、新しい見落としの発生源になることがある**
10. **テストは、実際に赤くなることを確認してから直す**。
    **赤くならなかった時、原因はテストの側にある。今のところ4つの型を踏んだ**（第36弾）:
    （a）**自己参照**…実装側の定数を、検査の範囲や入力にそのまま使っている。
    定数を緩めると検査も一緒に緩んで素通りする（`SAFE_HEAD`・`TAP_CAP` で2度）。
    守りたい約束は**具体の数字**で書く。
    （b）**条件が作れていない**…検査したい状況がそもそも組み立てられておらず、
    主張が自明に成立している（同着で「敗者が1人もいない」まま「敗者移動が無いこと」を
    検査していた）。**その状況が本当に起きているかを、検査の前に1つ確かめる**。
    （c）**分岐そのものを試していない**…実装に分岐があるのに、テストが片側の入力しか
    与えていない。条件は作れるのに、作りに行っていない（奇数人数で必ずできる3人1組を、
    偶数人数のテストだけで通していた）。**実装に分岐を書いたら、その場でもう一方の
    入力を1つ足す**。
    （d）**実データへの依存**…その時々のデータを検体に名指ししている。
    データが変われば赤くなるが、それは実装が壊れたのではない（「まだ完成していない
    ゲーム」の検体をゲーム名で書いていて、そのゲームが完成した日に赤くなった）。
    **変わるデータではなく、変わらない性質（門が効くこと）の側を試す**。
    **目印も、実データとぶつからないものを選ぶ**（第44弾）。
    「達成の数字が漏れていないか」を `99` という値で見ていたら、
    部屋コードの文字集合に `9` があり memberId も16進なので、
    **たまたま 99 が並んだ回だけ赤くなった**——たまに落ちる検査は、
    実装を疑わせるぶん、無いより悪いことがある。
    （e）**検査が例外を握り潰している**…検体を読む処理を `try/catch` で包み、
    失敗したら「該当なし」として先へ進んでいる。読めていないのに緑になる。
    CSSの選択子を切り出す時に `<style>` タグ自体を含んでしまい、
    最初の1件が `'<style>\n  body'` になって `matches()` が投げていた。
    catch が黙って false を返していたので、**わざと違反を混ぜた変異が素通りした**
    （第39弾）。**読めなかったものは、件数を数えて赤くする。**
    （f）**壊したつもりで、壊せていない**（第43弾。変異20件のうち3件が素通りして分かった）。
    「保存に失敗したら一言だす」を試すのに
    `win.localStorage.setItem = function(){ throw ... }` と書いたが、
    **jsdom の localStorage は代入を「その名前の項目を保存する」と解釈する**ので、
    保存はずっと成功していた。壊れていない状況で「直っている」を見ていた。
    しかも主張は `document.body.textContent` を見ていて、
    ハーネスが `public/js/*.js` を HTML に埋め込むため、
    **文言の定義そのもの**を拾って緑になっていた（10-e の親戚）。
    - **壊したら、壊れたことを1つ測る**（型(b) の変種）。
      「保存できていない＝古い値のまま」を先に確かめてから、知らせを見る
    - **「文字が画面にあるか」を `body.textContent` で見ない。**
      その中には `<script>` の中身も入る。**出たはずの要素**を名指しで数える
    - **flex の中に足した箱は、勝手に縮む**（指示49 49-2）。
      「はみ出しを測れているか」を見るために 900px の箱を足したら、
      親が縦並びの flex だったので **409px に縮められて、一度もはみ出していなかった**。
      `flex:none` を付けて初めて壊せた。
      **壊した後に「本当にその大きさになったか」を1つ測る**——
      ここでも「壊れたことを1つ測る」が効く
    （g）**片付いたあとに数えている**（第43弾）。
    `await FxKit.flash()` のあとに `.fx-flash` を数えていたが、
    その時には光は自分で片付いている。**門が効いていなくても同じ数**に見えた。
    出ている最中に数える。
    （h）**「起きなかった」は、呼ぶ道があって初めて意味がある**（第43弾）。
    振動を切ってから「震えなかった」を見ていたが、
    切り替えのハンドラはONの時しか鳴らさないので、
    **門を外しても誰も鳴らしに来なかった**。
    鳴らしに来る本物の道（`FxKit.vibe`）から呼んで、切／入の両方で見る。
    （i）**「立ち上げ直す」を、1つのキーだけで作らない**（第43弾）。
    端末に残るものを丸ごと持ち越さないと、
    **別のキーに印を書く実装**を素通りさせる。
    そこに足した型(b)がさらに1つ見つけた——その検体は一度も保存していなかったので、
    **既定値にもどっただけを「元にもどった」と読んでいた**。
    どれも「緑だから正しい」と信じると危ない形
11. **複数のテストプロセスを同時に走らせると、メモリを食い潰して信頼できない結果になる**。最終確認は何も並走させないクリーンな1回の実行で行う
    - ※**この項目は2026-09-09に読み直した（第44弾）。禁じているのは「無制限の並走」で、
      上限つきの並走までは禁じていない。**実測して上限を決め、道具の側に固定した。
      「クリーンな1回」の定義も、そこで次のように変わっている：

      | | 前 | いま |
      |---|---|---|
      | 走らせ方 | 1本ずつ（`&&` の連鎖） | **上限3本の並走**（`node tools/run-tests.js`） |
      | 実サーバーを立てるスイート | 区別なし | **単独で回す**（13本。コードから判定） |
      | 重いスイート | 区別なし | **単独で回す**（`wolf-vote`） |
      | 赤が出たら | そこで止まる | **最後まで走らせて、赤を一覧で出す** |
      | 合否 | 終了コードだけ | **スイート数・件数・終了コードの3つ** |
      | かかる時間 | 31分 | **17分** |

      **上限を3にした理由（勘ではなく実測）**：並走できる36本の合計は1386秒だが、
      そのうち `rt-screens` 単体が510秒ある。**1本で510秒かかるものがある以上、
      4本以上に増やしても全体は510秒より速くならない。**
      メモリは最悪の3本（shelf 2.5GB＋smoke 1.0GB＋rt-screens 1.0GB）で4.5GB、
      この機械の空き16GBに対して余裕がある。
    - **測る時は並走させない。**`npm run test:time` は `--jobs 1` に固定してある。
      並走した状態で測った時間は、他の本数で回した時の予測に使えない
    - **実サーバーを立てるスイートを「単独」に回すのは、ポートの衝突が理由ではない**
      （`listen(0)` なのでぶつからない）。**本物のタイマーとハートビートで進むから**で、
      他が回っていると時間の測り方が揺れる。
      どれが該当するかは**ファイル名ではなくコードから判定する**
      （`startTestServer` / `attachRealtime` を参照しているか）——
      名前で決めると、`room-edge`・`room-paths`・`room-ready`・`abnormal` のように
      `realtime` と付かないのに実サーバーを立てる4本が、静かに並走組へ落ちる
    - **1本20分の時間切れ**（2026-10-27・くまくんの決め）。rt-screens が終わらない待ちに入り、全テストが**8時間**止まったまま
      だれも気づかなかった。20分を越えたスイートは殺して**赤**（「時間切れ」と出る・回し直さない）。変えるのは `--limit-min`
12. **「動くはず」で終わらせず、実際に手を動かして確認してから報告する**。特に見た目・演出・タイミングに関するものは、テストが緑でも「確認した」とは言えない。実サーバーを立てて実際に操作する。
    **通信・状態だけを見るテストは、画面の不在を捕まえられない**（第36弾）。すごろく3ゲームで、
    部屋の画面が器（HTML）だけあって描画関数も呼び出しも無いまま「部屋版も完成」と報告していた。
    サーバーの進行役は正しく動き、socket.ioで実際に繋ぐテストも通っていた。
    **一覧に登録したことで満足せず、それを使う側に届いているかまで見る**（型1の一種）。
    恒久対策として tests/room-paths.js に「部屋のゲーム画面が描画に繋がっているか」の照合を置いた
13. **「直った」と報告する前に、本当に直っているか目で見て確認する**。前回報告と実態がズレた実例が複数ある
14. **画面遷移とサーバー確認は、操作の性質で使い分ける（どちらか一方を全部に当てはめない）**。
    （a）**本人の意思が確定している操作**（退室・とりやめ等）：先に画面を動かし、サーバーへの頼みは本人特定情報（部屋コード＋memberId）を添えて裏で送る。返事待ちにすると、通信が詰まった時に最大タイムアウト分ボタンが無反応に見える。
    （b）**存在が不確かな対象への遷移**（「部屋」ボタンで今の部屋に飛ぶ等）：逆に、遷移する前にサーバーへ確認する。古い記憶のまま消えた部屋に飛ぶと、新しい不整合バグを生む。
    どちらの場合も**状態の権威はサーバー**。socketのつなぎ直しをまたぐと socket.data の「このsocketは誰か」の印は消えるので、サーバーは空の頼みを**「ok」と返しながら黙って無視してはいけない**（第35弾Aの退室バグ。できていないのに ok を返すのが一番悪い）
15. **報告されたバグが手元で再現しない時は、デプロイ先で動いているコミットと手元の差を先に確認する**。未pushのコミットに入っている機能は本番に無い（開始3-2-1で実際に起きた。手元では全ゲーム動くのに、本番にはそもそも実装が無かった）
16. **自分が過去に下した安全性・仕様の説明を、後続の作業で無条件に前提としない**。特に「〜には渡らない」「〜は起きない」という断定は、実装を見て裏を取ってから使う（第35弾Aで「memberIdは本人の端末以外に渡らない」と説明したが、実際は部屋の全員に配られる部屋内共有IDだった。「サーバーだけが状態を持つ」のような前提も同様に、使う前に確かめる）
17. **「誰かがいなくなる」経路は必ず複数ある（切断・退室・kick・タイムアウト・部屋解散…）**。いなくなった後の処理（進行の数え直し・人数判定・残った人への知らせ）は、経路ごとに書かず**1箇所の共通関数に集約する**。第35弾Bで、切断にだけ数え直しがあり退室・kickに無かったせいで「最後の待ち相手が退室すると全員が無期限に待つ」進行停止が起きていた（`settleAfterMemberGone`に集約して解決）。新しいゲームの「待ち」処理を作る時も、まずこの共通関数を通す
18. **部屋の知らせ（公開ビュー）と本人の秘密（privateFor）は別々のメッセージで届き、順番の保証がない**。画面には「部屋はもう次の段階なのに、手元の秘密はまだ前の段階のまま」という瞬間が必ずある。その瞬間に古い秘密で画面を組み立てたり、「配られたものが無い」と誤判定して自動で返事を送ったりしない。**秘密のphaseが部屋のphaseに追いつくまで、その画面は何もしない**のが正しい。第35弾Bのdefuse説明画面で、役割を最後に選んだ人（自分の操作の返事より部屋の知らせが先に届く人）は毎回、初見の説明が丸ごと飛んでいた（自動読了レース）
19. **自作エンコーダー・フォーマット出力の検算を、同じ実装の逆関数（読み戻し）だけで済ませない**。配置・向きの系統的な間違いは、行きと帰りで打ち消し合って全テスト緑になる。独立した実装（別ライブラリのデコーダー等・テスト専用のdevDependencyでよい）と突き合わせて初めて検出できる。QRコードの形式情報が規格に対して転置されたまま、数学検算・読み戻し検算は全緑で、実機のカメラでは実装当初から一度も読めていなかった（8/18実機報告で発覚。独立デコーダーjsqrでの機械検証をテストに恒久化して解決）
20. **照合には向きがある。片方だけ見ていると、逆から入った不足を素通りする**。
    「カセットの全ゲームが進行役に登録されているか」は見ていたが、
    **「進行役の全ゲームがカセットに入っているか」は見ていなかった**。
    その結果、進行役を登録して ready:true にしても、ゲーム選択の画面に出てこない
    ——遊べない進行役は、作った人以外には存在しないのと同じ（第36弾・てふだ）。
    A⊆B を書いたら、その場で **B⊆A も要るか**を考える。
    「棚に出す」ために揃える手書きの一覧は、この時点で4つあった
    （開始設定・ready・カセットの games・画面の対応表）

21. **「設定は出るのに、何も起きない」を作らない**。
    性格表が「イベントを起こす」と宣言していても、EVENTS表にそのゲームの行が
    1つも無ければ、何も起きない。それでも設定画面には選択肢が出るので、
    遊ぶ人には「決めたのに効いていない」としか見えない（第36弾で4ゲーム該当）。
    **宣言と実データの両方を照合する**。あわせて「どの項目にも効き目の居場所がある」
    （盤を書き換えるか、その一巡だけ効くか）も機械で見る

22. **共通化してよい層と、そうでない層がある**。
    「待つ相手が1人もいない段階は、締め切りを待たずに進める」を芯（realtime.js）に
    入れたら、人狼の「朝」のように*誰も待っていないが見せるための段階*まで飛ばして
    投票に到達しなくなった（tests/abnormal.js が 7/11 に落ちて発覚）。
    **段階の意味はゲームごとに違う**。共通の芯に入れる前に、
    「その言葉は全ゲームで同じ意味か」を確かめる。違うなら、そのゲームの中で解く

23. **後から書いたCSSが、先にあった同名のクラスに負ける**。
    新しい画面のために `.au-shelf` を書いたが、その名前は
    別の機能がすでに使っていて、後ろにある古い定義が勝っていた。
    3列に並べたはずの棚が、幅ばらばらの2列で出ていた。
    **JSと違って、CSSの名前の衝突はどこからもエラーにならない**——
    テストは全部緑で、実機で見て初めて分かる（第38弾）。
    新しいまとまりを作る時は、そのまとまり専用の前置き（`mk-` など）をつける。
    既存の名前を使い回す前に、`grep ".名前[^a-z-]"` で先客がいないか見る

24. **検査の都合を、遊びの数字に持ち込まない**（落とし穴10-a の逆向き）。
    せり上げ式の持ち時間を8秒→30秒にしたら、実時間を待つテストが
    数分かかるようになった。ここで**持ち時間の方を縮めたくなる**が、
    それは遊びを検査に合わせて歪めること。
    正しいのは検査の側に早送りの道具を作ること（`rush()`）。
    ただし早送りだけにすると「締め切りが本当に効くか」を誰も見なくなるので、
    **実時間で待つ検査を1件だけ残す**（第38弾）
    - **「◯ms待つ」で書いた検査は、速さの設定を変えた日に嘘をつく**（第44弾）。
      扉の待ちを外したら、`await sleep(win, 200)` のあとに演出を見ていた検査が
      「出ない」と言い出した。**待ち方を「時間」ではなく「出たか」に変える**
      （`waitFor`）と、どちらの速さでも成り立つ
    - **速さを変える時は、演出そのものを見ている検査を先に数える。**
      一度「演出の速さ」を丸ごとスキップにしたら、**8件が赤くなった**——
      縁の光・爆発の閃光・処刑の発表・お祝い・開示の順。
      どれも「スキップだと出ないのが正しい」ので、赤は実装の話ではない。
      測り直したら、欲しかったのは**扉の0.5秒だけ**で、
      それ以外のスキップは1秒も稼いでいなかった。**広く効かせる前に、幅を測る**

25. **手で書いた検体は、実装から静かに離れていく**（落とし穴10-d の親戚）。
    画面テストの偽データを手書きしていると、
    **サーバーが送らない形を画面が読めてしまう**。
    どちらも自分で書いているので、両方が同じ間違い方をしていても気づかない。
    検体は本物の進行役を動かして作る（`auStage()` が auction-room.js を
    実際に動かし、publicView / privateFor をそのまま画面へ流す）。
    こうすると、秘密の落とし方まで本物と同じものが検査される（第38弾）

26. **`position:fixed` は「画面に固定」ではない**（落とし穴23の親戚・CSSは何も言わない）。
    先祖に `filter` / `transform` / `backdrop-filter` / `perspective` が
    付いていると、**そこが基準になり、画面ではなくページの座標に置かれる**。
    `#app` は明るさ補正のため `filter:brightness(...)` を常に持っていたので、
    長い画面（設定・記録・カタログ）でダイアログを開くと、
    実測で812pxの画面に対して y=1015〜1388——**完全に画面の外**だった。
    遊ぶ人には「押したのに何も出ない」としか見えない。
    **サーバーも状態も socket も正しいので、通信を見るテストでは捕まらない**
    （落とし穴12の型。実サーバーで実際に測って初めて出た）。
    重なりは `#app` の外（`#uiLayerRoot`）に置く。
    見張りを書く時は **`#app` を名指ししない**。基準を作りうる指定を全部集めて、
    置き場の先祖ぜんぶと照らす——あとで誰かが `body` に足した日にも赤くなるように
    （第39弾）

### バグを探すときの2つの視点（第35弾Bの監査で一般化した型）

上の落とし穴が「過去に起きた具体的な事故」の記録なのに対して、これは「次に何を疑えばいいか」の視点。新しい機能のレビューや監査では、この2つの型で探すと見つかりやすい。

- **型1「共通化の境界面での取りこぼし」**：集約の設計は正しいのに、末端が1つ漏れる／片方だけ古い。実例：話し合い画面は12要素を個別に隠していたが`micStatus`だけ漏れた（あれそれの音声判定表示がワードウルフに残留）／盤面の死因対応表が決着画面の対応表と別に存在し、存在しないキー`vote`のまま古びていて処刑が「襲撃」と誤表示された。**探し方**：「同じ意味の一覧・対応表・非表示リストが2か所以上に無いか」をgrepで横展開する（実際にこの方法で勝敗文言の並走コピーを先回りで特定できた）
- **型2「境界をまたぐ状態のリセット判断」**：状態変数がフェーズ・試合・ゲーム・日付のどの境界でリセットされるべきかの判断が1つずつ違い、間違うと漏れる。実例：`pairNote`の「初めての組み合わせ」は日付境界の判定が片側だけで「初めて」と「長い付き合い」が同時表示された／`state.voiceDetect`はゲーム境界を越えて漏れた（修正済み）／`play.aiFailStreak`は試合をまたいで持ち越すのが正しい（AIが落ちている状況は連続だから。意図的）。**探し方**：`docs/監査_状態と境界.md`の一覧で「この状態はどの境界で消えるべきか」を1つずつ確認する

### 残骸・漏れが出ない良い型（第35弾Cの監査で言語化。新しい画面・演出・共有部品はこの型で作る）

落とし穴が「事故の記録」なのに対して、これは監査で「漏れが構造的に出ない」と証明できた実装のお手本。

1. **両方向出し分けの共通関数**（`setupPlayTimerUI`型）：「出す側」と「隠す側」を別々の場所に書かず、**現在の状態から表示を計算する関数1つ**を全分岐が通る。片方向の隠しリスト（micStatus事故の型）はこれで置き換えられる
2. **毎描画の自己リセット**（部屋系画面の型）：描画のたびに`innerHTML`を組み立て直す。前回の表示が構造的に残れない（`scr-rt-play`・`scr-rt-quiz`・大画面の中身）
3. **入場時リセット＋照合の掃引**：画面やゲームに入る瞬間に前回分を消す（`bombWireOverlay`・`correctPickerOverlay`・defuseの`dfBrief`）。監査するときは**leave/enter関数×常駐状態変数の全照合**で「拾われていない変数」を機械的に探す（第35弾Bの掃引手法）
4. **中央集約＋デナイリスト方式**（スキップ・テーマの型）：設定は**出す側に条件を書かせず**、1か所で効かせる（スキップ＝`.fx-skip`全停止CSS＋`FxKit.init({ms:fxMs})`＋`fxMs()`の三層／テーマ＝`goTo`→`applyGameTheme`の1本道）。適用範囲は**「除外だけを列挙」**して、新しく足したものにはデフォルトで適用される向きにする（テーマの`THEME_FREE_SCREENS`。追加し忘れ＝適用され過ぎ、という安全側に倒れる）。手書きの除外リストは正本（`tests/inventory.js`）との照合テストで腐りを防ぐ
