# 障害と復旧の記録：旧VPSの消失（2026-09）

## 何が起きたか

ConoHaの旧VPS（メモリ1GB・Ubuntu 24.04）が、**料金のチャージ忘れによりサーバーごと削除された。**
GitHubにあるコードは無事だったが、**サーバーの上にしか無かったものは、すべて失われた。**

## 何を失ったか

| 失ったもの | 中身 | 取り戻せるか |
| --- | --- | --- |
| `data/aresoredorekore.db` | アカウント・お題・対戦履歴・称号・2人組の記録 | **不可**（バックアップが1つも無かった） |
| `.env` | 登録コード・セッション署名鍵・Gemini APIキー | 作り直し（値は新しくなる） |
| サーバー上の設定 | cron（自動反映）・Nginx・pm2・ufw・Let's Encryptの証明書 | 作り直し |

**一番痛かったのは、失ったこと自体より「作り直す手順がどこにも書かれていなかった」こと。**
自動反映のcronも、Nginxの設定も、サーバーの中にしか無かったので、サーバーと一緒に消えた。

## どう直したか

1. 新しいVPS（メモリ2GB・Ubuntu・`133.88.118.211`）を契約
2. 復旧の手順そのものを**リポジトリの中に置いた**（→ `tools/vps-setup.sh`）。
   次に同じことが起きたら、`git clone` してこれを1本流せば戻る
3. `.env` を作り直した（登録コードは新しい値。**値はリポジトリに書かない**）
4. データベースは真っ新から。テーブルは `db.js` が起動時に `CREATE TABLE IF NOT EXISTS` で作る
5. DuckDNSのドメインを新しいIPに向け直し、Let's Encryptを取り直した

**2026-09-01、復旧完了。** サーバー上の作業（SSH・セットアップ・DNS・証明書・疎通確認）は
くまくんが実行し、その結果の報告にもとづいてここに記録している
（コード・スクリプト・手元での動作確認はClaude Code側で行った）。

| | 状態 |
| --- | --- |
| アプリ | 稼働（`https://aresoredorekore.duckdns.org/`） |
| HTTPS | 取得済み。2026-11-30期限・以降は自動更新 |
| 自動反映 | 2分おき（`tools/deploy.sh`） |
| DBバックアップ | 毎日4:10（日次14世代＋月次12世代・整合性チェック付き） |
| ConoHa自動バックアップ | 有効 |
| 登録の合言葉 | 3つ（値は `.env` のみ） |
| DuckDNSの見張り | **未設定**（任意。手順は `tools/duckdns-update.sh` の先頭） |

**失ったのは旧データベースの中身だけで、コードと機能はすべて戻った。**
バックアップ・自動反映の権限問題・iPhoneで打てない合言葉が直ったぶん、
**復旧後のほうが、消える前より安全な状態になっている。**

## 次に同じことが起きないための備え

### 1. データベースの毎日のバックアップ（今回追加）

`tools/backup-db.js` を cron で毎日 4:10 に走らせる。

- **置き場所**：`/root/backups/aresoredorekore/`
- **世代**：日次14世代（2週間さかのぼれる）＋ 毎月1日の分を12か月
- **`cp` ではなくSQLiteのオンラインバックアップAPIを使う**。
  DBはWALモードなので、遊んでいる最中に `cp` すると、まだ本体に書かれていない
  `-wal` の中身が抜けた**壊れたバックアップ**が黙って出来る
- **取った直後に `integrity_check` して、アカウント件数を数える**。
  「毎日動いていたのに、いざ戻そうとしたら開けなかった」を防ぐため
- 自動反映（`tools/deploy.sh`）でコードを入れ替える直前にも、1つ取る

**戻し方**（サーバーで）：

```
pm2 stop aresoredorekore-backend
cp /root/backups/aresoredorekore/daily/YYYY-MM-DD.db /root/backend/data/aresoredorekore.db
rm -f /root/backend/data/aresoredorekore.db-wal /root/backend/data/aresoredorekore.db-shm
pm2 start aresoredorekore-backend
```

### 2. 手順をサーバーの外に出した

`tools/vps-setup.sh`（サーバーの組み立て）と `tools/deploy.sh`（2分おきの自動反映）は、
これまでサーバーの中にしか無かった。**リポジトリに移したので、サーバーが消えても手順は残る。**

`tools/duckdns-update.sh` も足した。IPは固定なので普段は要らないが、**DuckDNSは長く更新の無い
ドメインを消すことがある**。ドメインが消えれば、サーバーが元気でも誰も辿り着けない——
今回と同じ「アプリは無事なのに繋がらない」形になる。トークンを `/root/duckdns.env` に置くと、
`vps-setup.sh` が5分おきの見張りをcronに入れる（トークンは秘密なのでリポジトリには置かない）。

### 3. 2つのバックアップの役割分担

**どちらか片方だけでは足りない。守っている範囲が違う。**

| | ConoHaの自動バックアップ（オプション・有効化済み） | アプリ側のバックアップ（今回追加） |
| --- | --- | --- |
| 守る範囲 | **VPSまるごと**（OS・設定・`.env`・DB） | **データベース1ファイルだけ** |
| 効く場面 | サーバーが消えた・OSが壊れた・今回のような事故 | DBが壊れた・間違って消した・変な記録が入った |
| 戻す速さ | 遅い（イメージからサーバーを作り直す） | 速い（ファイルを1つ置き換えるだけ） |
| 戻す粒度 | その時点のサーバー全部（DBだけ戻すことはできない） | 日付を選んでDBだけ戻せる |
| 弱点 | 世代が少なく、DBだけを戻せない | **VPSごと消えたら道連れ**（同じディスクの上にある） |

つまり、**今回のような「VPSごと消える」事故はConoHa側でしか救えず、
「DBだけおかしくなった」はアプリ側でしか素早く救えない。**

### 4. まだ残っている弱いところ（承知の上で残しているもの）

- **アプリ側のバックアップは同じサーバーの中にある。** VPSごと消えれば一緒に消える。
  外（別のストレージ）へ運ぶには置き先の認証情報が要るので、今回は入れていない。
  ConoHa側の自動バックアップがこの穴を埋めている前提
- **チャージ忘れは、仕組みでは防げていない。** ConoHaの残高アラートメールを見る運用でしか防げない。
  今回の原因はここなので、**支払い方法の見直し（自動チャージ等）が、一番効く再発防止**
